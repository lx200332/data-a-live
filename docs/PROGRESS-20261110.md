# 2026-11-10：第一次进入 iOS 桌面

这份记一天之内走完的路：从「GPU 卡在 `release CM3 reset`」到「SpringBoard 起来、桌面画出来」，
以及进桌面之后测到的三个真问题。所有数字都来自当次真机的内核日志，不是估计。

机型小米 17 Pro Max（popsicle / 2509FPN0BC / SM8850 / Adreno 840 / 4 KiB 页 / 面板 1200x2608 stride 4800）。
引导方式是 `fastboot boot`，根文件系统是安卓 userdata 里一个 pin 住的 16 GiB HFS+ 文件。

## 一、结论先说

| 部分 | 状态 |
|---|---|
| GPU（GMU / 固件 / SMMU / CP / HFI / 15 级初始化） | **通**。`fw init result 00000100 BOOTED`、`GX ON`、`level 1` 到 `level 14 (user interface) done` 全过 |
| AMFI / 代码签名 | **通**。`code signature validation failed` 0 次、`initproc failed` 0 次、`restart type` 0 次 |
| 内核 | 8/8 CPU、`lo0/gif0/stf0`、`AppleCLCD 1200x2608 stride 4800`、`AppleARMBacklight` |
| 用户态 | launchd → SpringBoard → backboardd → lsd，桌面出来，整轮 318 s 没崩 |
| Metal 合成 | **能画，但慢**。1672 个 command buffer / 116215 次 draw，然后 backboardd 被 OOM 杀掉重启 |
| 帧率 | 黄金镜像 120.0 fps；本版 42.6 fps 且抖动（见第四节） |
| 色彩 | DPU 寄存器与黄金逐字相同；观感异常的来源不在 DPU（见第四节） |

## 二、AMFI：三层根因，前两层一直在，第三层才是致命的

`PANDORA GPU: next: GMU: release CM3 reset` 之后线程静默消失、无 panic、其他 CPU 正常，
前后查了很久：SMMU SCTLR bit26、`dsb osh` 等设备应答、GMU AHB fence vote，全部排除。
真相是**同一时刻整机被 `restart type 4` 复位了**，GPU 线程是被复位一起干掉的，不是 GMU 挂住。

复位的链条：

```
AMFI: '.../dyld_shared_cache_arm64.01' is adhoc signed.
AMFI: code signature validation failed.
dyld cache '(null)' not loaded: (null)
Library not loaded: /usr/lib/libSystem.B.dylib   (Referenced from /sbin/launchd)
pid 1 exited -- exit reason namespace 6 subcode 0x1
initproc failed to start -- PANDORA: restart type 4
```

三层原因，按发现顺序：

1. **本地重链用的是 11-03 的陈旧目标文件。**
   `/opt/work/ci/obj/DEVELOPMENT_ARM64_PANDORA/security/DEVELOPMENT/mac_base.o` 时间戳 2026-11-03 14:24，
   而源码 `security/mac_base.c` 11-06 已含补丁 0337（`sweet_dyld_policy_enabled`，打印
   `SWEET AMFI: dyld policy answered by the kernel`）。`mac_vfs.o` 同样陈旧，缺 0336。
   两个 `.o` 里相关字符串 0 命中。所有用 `local_relink.py` 打出来的内核都缺这两个补丁。

2. **`xnu-cc.py` 不接受 `-o`。** 它自己按 `<component>__<basename>.c.o` 生成目标名，
   丢弃传进去的 `-arch` / `-MF` / `-o`。CI 日志里的编译行本来就没有 `-o`，
   正确用法是把 CI 行原样喂给它，`bt` 参数传 `.../buildtree`（不是 `.../buildtree/xnu`）。

3. **trust cache 比黄金镜像少 7 条 cdhash。** 这是最致命的一层。

   | 模块 | 黄金 `loader-boot.img` | 我们用的 | 差 |
   |---|---|---|---|
   | 模块 0，uuid `9f368a73d90b40ce943c827e13e72eee` | 2762 条 | 2760 条 | 2 |
   | 模块 1，uuid `7dd0aed78907d26577ae14dd4363e5e3` | 98 条 | 93 条 | 5 |

   多出来的 7 条：

   - 模块 0（flags `00000000`）：`161b7051fe7fdffaef243396321451c4334877ed`、`179ee0de5740f316de40221e17c86661cf58e284`
   - 模块 1（flags `02000200`）：`137f323405f3fe1558084d3a77e7664a60beb0f8`、
     `4ba3d4ec12a0f2c0fd52367c69ba3e73a7cd9922`、`5bdf5dbcd4a4923d69bab08d82c7eae952d66d25`、
     `b5ca7bc6bd12ac5073410f9965908ca0bbff7b1b`、`d0ec4920c86130990ad40cb5b6891b3efb51f4d1`

   这几条就是 adhoc 签名的 dyld 共享缓存和 launchd 自己的 cdhash。补上以后一次通过。

顺带记一个**不能用的开关**：`sweet_cs_bypass=1`（0336）会让 `mac_vnode_check_signature`
直接返回 0 但不填 `cs_blob`，AMFI 的 execve hook 判成 `no code signature`，
`hook..execve() killing pid 1: no code signature` → SIGKILL pid 1。这个参数只能给非 initproc 用。

## 四、桌面状态下测到的三个真问题

### 1. 每帧重编译 pipeline（帧率与卡顿的唯一根因）

同一条统计行，黄金与本次对比：

```
黄金 boot44.log   T0 V cache hit22 miss0 wr0        T pipeline n=22  total=43ms    max=6ms
本次 klogG        T0 V cache hit0  miss132 wr132    T pipeline n=52  total=3451ms  max=110ms
                  T1 hit0 miss327 · T2 hit0 miss381 · T3 hit0 miss511
                  T2 T pipeline n=140 total=10552ms max=127ms
```

黄金 22 个 pipeline 建一次就永久复用；本次 **535 个互不相同的 key，一个都不命中**，
同一个 boot 内后续 30 秒窗口照样 `hit0`。每次提交都要现场编译 Vulkan pipeline，单次最长 127 ms。

后果直接反映在帧率上：

```
黄金   600 frames in 5000 ms  → while animating 600, avg 8333 us = 120.0 fps
本次   600 frames in 17705 ms → 87.2 fps
       600 frames in 65193 ms → 9.2 fps
       600 frames in 18902 ms → 31.7 fps
       while animating 506, avg 23460 us = 42.6 fps
```

注意 `copy avg` 两边一样（3900 vs 4044 us）——**每帧 4 ms 的 CPU 拷贝不是瓶颈，瓶颈是重编译**。

### 2. GPU 内存池涨到 977 MiB，触发 OOM，backboardd 被杀重启

```
105 s  alloc 2762  map 3046  pool 758/1024 MiB
110 s  alloc 4166  map 4463  pool 824/1024 MiB
111.450  native-metal: command buffer refused: endEncoding: OutOfMemory(Device)
115 s  alloc 4695  map 5030  pool 977/1024 MiB      ← 顶点
210 s  client 0: -                                   ← backboardd 消失
215 s  alloc 86    pool 129/1024 MiB                 ← 重启，计数归零
```

黄金全程 `pool 518 of 1024 MiB`，从 20 s 到 210 s 一个字节不涨。
535 个 pipeline 对象就是泄漏源。

同时 `trying to set state of nil layer` 103 次（黄金 0 次）、`|SpringBoard|` 日志 1045 行（黄金 0 行）。

### 3. 色彩与刷新率：DPU 配置是对的

DPU 寄存器逐字对拍（黄金 vs 本次）**完全一致**：

```
MDSS hw d0000000 · ctl0 top f0020000 · vig0 format 000237ff unpack 03020001 src 0a300258 stride 000012c0
lm0/lm1 op 00000000/80000000 out 0a300258 · intf1 config 00800000 format 00002100 mux 000f0000
SMMU SMR 2 80020800 S2CR 00000002 (translate, bank 2) · bank 2 sctlr 000000e0 actlr 00000003
```

背光也一致：`backlight-level = 32768 (0x8000)`、`brightness correction 0x10000`、
`CompensationTweak cap 131072 scaler 65536`。

所以「颜色不对」不是位深或通道顺序配错。实际发生的是：

- `sweetfb_fill=1` 生效中，画面是 1125x2436 **最近邻**放大到 1200x2608
  （x1.067 / y1.071，宽高比差 0.4%）。放大 6.7% 的最近邻会让文字边缘和图标出现单像素错位，
  主观上就是「发虚、串色」。
- OOM 之后 30 次 `pandora-metal refused`，合成失败的帧图层是空或残留上一帧，
  视觉上是忽明忽暗。

刷新率方面：`sweetfb_hz=60` 是 cmdline 写死的（`fFlushTicks = 1`，
打印 `present up to 60 Hz (every 1 ticks)`），面板支持 120/90/60/30 Hz
（DTS 四个 timing 块 framerate `0x78/0x5a/0x3c/0x1e`）。但**先修 pipeline 再谈刷新率**：
现在连 60 Hz 都跑不满。

### 附：scanout 从来没成过，两边一样

`SWEET FB: scanout on: 0 frames scanned out, 600 copied`，每份 stats 都是 0。
`display interrupts 0 (0 frame starts)`。黄金也是 0，所以这不是本轮回归。
原因在 `SweetFramebuffer.cpp:1451` 的资格检查要求 surface 格式是 `SWEET_FB_FORMAT_BGRA`
（`0x42475241`），而 backboardd 的图层是 `0x62336138`（`'b3a8'`）。
每帧走 CPU memcpy 进 panel memory，代价 3.9-4.8 ms。这条以后单独处理。

## 五、构建链（可复现）

`wsl/make_image.sh` 七步，本轮实测每一步都必要：

1. DUAL 判定（`pandora_pspill`，out32 命中 → `--amp`）
2. `mkprelink.py native kc.macho prelinked`（11 个 kext，110 个原厂类，209 个 vtable 槽）
3. `patch_amfi.py prelinked.raw prelinked`（门禁 0，P1P2）
4. `mkadt_pandora.py --gpu-pool 1024 --amp --root-extents --log-extents --fw-extents`
   然后 `adt_merge_chosen.py` **只补 `mac-address-wifi0`**
5. cmdline（605 B，从 `ct5-flash.img` 的 payload 里取）
6. `make_image --tc "tc-mod0 tc-mod1"`（两个 trust cache）
7. `topo_check.py` + `final_check.py`

两个坑写在脚本注释里但很容易踩：

- **root extents 不能全量 merge `ref.adt`。** 那是 11-03 另一台设备的布局（2275 段，
  first phys 2341888），当前设备是 1208 段（first phys 5198839808）。
  照抄会把内核指向错误物理块，挂根必败。
- **`adt_off` 是相对 payload 起点 `0xb000` 的偏移**，不是相对内核文件起点。

## 六、下一步

1. **修 pipeline cache key。** `pandora-metal cap pipe` 里 535 个 hash 各不相同，
   嫌疑是 cache key 混进了不稳定成分（`VK_ERROR_INVALID_DRM_FORMAT_MODIFIER_PLANE_LAYOUT_EXT`
   出现 9 次）。前端的 `V cache hit0 miss132 wr132` 在 `tools/metal/adapt_ios16.py`
   生成的 `NativeBridgeMetalFrontend.mm` 里，不在内核驱动。
2. 修完复测：帧率、`pool` 是否稳在 518 MiB、`OutOfMemory` 是否归零、颜色跳变是否消失。
3. `sweetfb_hz=60` → 120，`sweetfb_fill` 改双线性或关掉换居中。
4. 之后才轮到 scanout（surface 格式门槛）和 ADSP（`pandora_slot=a`）、
   AKS selector 10、SpringBoard 的 `hint 2` 同步 mach_msg 对端。
