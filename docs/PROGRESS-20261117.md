## 2026-11-17 · WiFi：iATU 窗口、有界 dump，以及三次「域没上电就盲扫」

这份接 `popsicle-port/STATUS-20261117-WiFi-iATU映射与有界dump.md`。
那边记的是驱动怎么改，这边记的是**这轮把哪些"未知"变成了"读数"**，
以及一个必须留给下一个人的警告：`0x6b004` / `0x6c000` 这两个 GDSC 偏移是从 SM8550 推定的。

一句话：**iATU 与 BAR0 两个 > 4 GiB 的窗口已经能映射成功并拿到 VA；PARF 与 pcie_sm 两处
dump 都已设上界；但四次上机没有一次跑到 GDSC 上电那一步 —— 第二次死的偏移（`parf[0x58]`）
和第三次的（`pcie_sm[0x1048]`）说明问题不是"上界定小了"，是"对未上电的寄存器块逐字扫"。**

## 一、iATU：为什么它是 BAR0 读不到的唯一原因

真机 `/soc/pcie@1c00000` 的 `reg` 六段，第五段就是 iATU：

```
reg = <0x0 0x1c00000    0x0 0x3000          /* parf   */
       0x0 0x1c06000    0x0 0x2000          /* phy    */
       0x0 0x400000000  0x0 0x10000000      /* dm_core */
       0x0 0x4000f200000 0x0 0xa8           /* elbi   */
       0x0 0x410000000  0x0 0x1000          /* iatu   */
       0x0 0x1d07000    0x0 0x7000>;        /* pcie_sm */
```

`0x410000000 + 0x1000` = **8 个区 × 0x200**，正是 DesignWare 的 unrolled 布局。
`popsicle_wifi.c` 从头到尾没写过这块，所以：

- BAR0（`0x40400000`，2 MiB，与 `/proc/iomem` 的 `cnss` 保留区同址）读回全 0；
- ELBI（`0x4000f200000`）单独碰一下就整机中止 —— 它同样在出站窗口后面。

Linux 主线的写序（`dw_pcie_prog_outbound_atu()`）：

```
LOWER_BASE → UPPER_BASE → LIMIT → [≥460A] UPPER_LIMIT
           → LOWER_TARGET → UPPER_TARGET → CTRL1 → CTRL2(含 ATU_ENABLE)
```

两条易错的寻址路径，**不能混用**：

| 路径 | 编码 | 判据 |
|---|---|---|
| unrolled（v4.80a+） | `atu_base + (index << 9)`，IB 再或 `BIT(8)` | `IATU_VIEWPORT` 读回 `0xFFFFFFFF` |
| viewport（老式） | `IATU_VIEWPORT = dir \| index` | 否则 |

vendor 驱动里写的是 `CTRL_2 = 0x80000000 \| (index << 16)`（Qcom 私有），
**和 Linux 的 `dir | index` 不是一套**。驱动里两套宏都留了，判定放运行时。

**关键区分：编程窗口是安全的，读穿它才是不安全的。** 所以那次唯一的穿透读
（`0x100`/`0x104`，期望 `0x17cb`/`0x110e`）单独放在 `wifi_bar0read=1` 后面，
在链路训练完成之前不要打开。

## 二、四次上机，读数原文

| 镜像 | 环行数 | 结果 |
|---|---|---|
| `boot-yx` (`e672f829…`) | **0** | 死得比 1 s console flush 早，rawhash 仍 `b69dae56…` 全零 |
| `boot-yy` (`d0d87009…`) | 561 | iATU/BAR0 映射成功；驱高 gpio16/18 之后静默 |
| `boot-yz` (`bcf7d39e…`) | 586 | 死在 `parf[0x58]` |
| `boot-za` (`d4722df6…`) | 593 | fix1 后 PARF 22 字读完，死在 `pcie_sm[0x1048]` |

`boot-yy` 的完整 wifi 段（17 行，按预期全部打印）：

```
[0.169] popsicle_wifi: FastConnect 7900 survey … (wifi_poweron=1: step 0 will WRITE gpio16/gpio18)
[2.170] popsicle_wifi: wifi_delayms done, starting the survey
[2.170] popsicle_wifi: mapping TLMM 0xf100000 + 0xce000        → 0xfffffff8b02a1000
[2.170] popsicle_wifi: mapping iATU 0x410000000 + 0x1000 (above 4 GiB) → 0xfffffff8afe35000
[2.170] popsicle_wifi: mapping BAR0 0x40400000 + 0x1000        → 0xfffffff8afe36000
[2.170] popsicle_wifi: power-on wlan-en (gpio16) after cfg=0x00000200 io=0x00000003 OK
[2.170] popsicle_wifi: power-on sw-ctrl (gpio18) after cfg=0x00000200 io=0x00000003 OK
（无 step1、无 abort、无 esr）
```

**这一轮最重要的新事实**：`0x410000000` 这种 > 4 GiB 的物理地址**能映射成功**
（`ml_io_map_unmappable` 返回非零 VA），所以「高位窗口不能用」这条假设作废。

`boot-yz` 与 `boot-za` 的 `grep 'abort|esr|panic'` 都是零命中 —— 不是可报告的 data abort，
是静默复位。

## 三、三次同形事故，说明的不是「上界太小」

| 次数 | 位置 | 结果 |
|---|---|---|
| 1（蓝牙，11-12） | 扫 `gcc[0x3b000]` | `esr 0x96000010` / `far 0xfffffff8d3d04000`，整机复位 |
| 2（WiFi，YZ） | `parf[0x58]` | 静默复位 |
| 3（WiFi，ZA） | `pcie_sm[0x1048]` | 静默复位 |

`boot-yz` 是 `0x00..0x7c` 连读 32 字，死在 0x58；`boot-za` 把上界收到 0x54 立刻通过，
然后死在另一块 `pcie_sm` 的第十四个字。**这不像"边界画错"，像"这块内存现在根本不该碰"。**

三次的共同前提是同一个：**`step4` 的 GDSC 上电从来没执行过**（`grep step4` 在四份 klog
里全零命中）。所以所有 dump 都是在「PCIe 两个 GDSC 域还在断电」的状态下做的。
`/sys/kernel/debug/clk/clk_summary` 侧面支持这一点：`pcie_0_gdsc` 与 `pcie_0_phy_gdsc`
的 `hardware enable` 在 Android 里是 `N`，直到 `msm_pci` 真正 probe 才翻成 `Y`。

结论：**先上电，再 dump。** fix2 把 `wifi_step4_power()` 提到 `step1/2/2b/2c` 之前，
`boot-zb` 已就绪未上机。

## 四、必须留给下一个人的警告：两个 GDSC 偏移是推定的

```
GCC_PCIE_GDSC      0x0006b004   /* pcie_0       */
GCC_PCIE_PHY_GDSC  0x0006c000   /* pcie_0_phy   */
```

这两个值来自 `gcc-sm8550.c` 的 `.gdscr = 0x6b004 / 0x6c000`（同族的 `qdu1000` / `sm7150` /
`sc7280` 偏移一致），**不是从 SM8850 上读出来的**。同一次探测里可读的对照是：

```
gcc[0x39004] = 0xfa22f800   usb30_prim GDSCR  bit0=0 -> 已上电（已知真值）
gcc[0x6b004] = 0x0222f801   pcie_0       bit0=1 -> SW_COLLAPSE 断电
gcc[0x6c000] = 0x02222801   pcie_0_phy   bit0=1 -> 断电
```

`0x39004` 那位是真值（USB 一直工作），另外两位**在 Android 侧没有对照过**。
下次上机如果 `step4` 报 `a domain did not report up`，第一件事是去 Android 侧
`clk_summary` 与 `clk_print_regs` 里找 `pcie_0_gdsc` 的真实偏移，而不是继续调轮询。

同理，`CFG_GDSCR` 的 `POWER_UP_COMPLETE`(bit16) / `POWER_DOWN_COMPLETE`(bit15)
是 `drivers/clk/qcom/gdsc.c` 的通用定义，**但读回 `0` 绝不能当成功** —— 这一轮已经
因为这条栽过一次（见下）。

## 五、这一轮修掉的三个真 bug

| # | 位置 | 现象 | 修法 |
|---|---|---|---|
| 1 | `wifi_gdsc_on()` | `return (cfgv & POWER_UP_COMPLETE) != 0 \|\| cfgv == 0;` —— 域读回 0 也算 up | 显式拒绝 `cfgv == 0`，打印 `treating it as NOT up` |
| 2 | `wifi_step0_power_on()` | `delay_for_interval(2000, NSEC_PER_USEC)` 注释写 2 s，第一参是**微秒** ⇒ 实际 2 ms | 改 `20000` |
| 3 | `rlx??.sh` 对象来源 | `popsicle_wifi.o` 在 CI 对象树里**根本不存在**，全靠一行 `cp`；cp 失败时重链静默用上一代对象 | 加对象来源守卫：缺文件 `FATAL … exit 2`，存在则打印 `ls -l` + `md5sum` |

第 3 条与蓝牙那次 `ccbt5.sh` 硬编码源路径（改源码不生效、`compiled 1/1` 但 obj 不变）
是同一类错误 —— **重链脚本必须先证明它用的是哪个 .o**。

## 六、`wifi_delayms` 为什么必须存在

第一次带 `wifi_iatu=1` 引导（boot-yx）产出**空环**：rawhash 仍是全零的 `b69dae56…`，
`klog` 0 行。原因是线程在 `0.2 s` 就摸到 `0x410000000`，
而 `pl_thread` 的 console flush 间隔是 1 s（`pandora_logsecs` 缺省 3，块 0 每轮重写）。
**死得比第一次 flush 早 = 日志一字节都不落盘。**

加 `wifi_delayms=2000` 后（boot-yy）环活了，17 行 wifi 日志全在。

这条经验对蓝牙也成立（`boot-yx` 就是同一形状）。**任何"第一次碰新 MMIO"的代码
都应该先睡过第一个 flush 窗口。**

## 七、留给下一个人的接力点

1. `buildZB.sh` → `boot-zb.img` → 上机。要看的四件事：
   `step4` 是否打印 `both domains up`、`parf[0x414]` 的 bit7 是否终于置位、
   放宽后的 32 字 dump 能否整段读完、`pcie_sm` 十四字是否也能读完。
2. 若 `step4` 仍报 `a domain did not report up`：**去 Android 侧证 `0x6b004`/`0x6c000`**，
   不要在轮询上打转（见第四节）。
3. 域上电之后才是 M1 真正的里程碑：`wifi_iatu=1 wifi_bar0read=1` 读 `0x100/0x104`，
   期望 `0x17cb/0x110e`。**在那之前不要开 `wifi_bar0read`。**
4. M2（BHI/BHIE 两段式）见 `popsicle-port/wifi-facts.md` 与
   `wifi-extract/` 下的 `amss20.bin` 解析：外层 `EM_ARM @0x0`、内层 `EM_HEXAGON @0x80000`、
   再 512 KiB 签名尾；`sbl_size = SZ_512K` 正好落在内层头上，所以必须两段
   `[0,0x80000)` 与 `[0x80000,0x6fb040)`，后者 13 个 BHIE 段、向量表 208 字节、
   **`bhi_vec_entry` 是 16 字节不是 8** —— 这是全篇最容易写错的一步。
5. WiFi 的 8 条电源轨同样要按 `regulator_summary` 的实跑值填，**不要抄 DTS 的
   `init-microvolt`** —— 蓝牙七路就是这么错的（DTS 852/1256/1857 vs 实跑 892/1224/1800）。
